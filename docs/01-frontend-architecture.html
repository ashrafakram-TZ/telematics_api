1 What Technologies We Used & Frontend Structural Architecture

Our telematics system connects physical edge vehicles, a high-throughput MQTT switchboard, a NestJS database ingestion engine, and a modern React 19 web dashboard. Below is the foundational stack and structural layout of the codebase:

1. Frontend Web App

Telamatics_web: Built with React 19, Vite 6, and Tailwind CSS 4. Adopted design tokens and standardized CVA primitives from IAM/Tenant.

2. Routing & State

TanStack Router for file-based type-safe routes and TanStack Query for caching, background syncing, and automatic re-validation without manual refresh buttons.

3. Backend Ingestion API

Telematics: Built with NestJS 10, TypeORM, and PostgreSQL 16. Subscribes to telemetry topics and persists historical vehicle tracks and geofence alerts.

4. Live Map & Realtime Engine

Leaflet for rendering smooth moving car pins, and MQTT.js over WebSockets with sessionStorage Client IDs to prevent multi-tab kickoffs.

2 Backend Integration & Telemetry Data Pipeline

The NestJS backend server (Telematics) acts as both an MQTT consumer and a REST API provider. Here is how incoming packets are processed and stored:

1. MQTT Event Listener

On boot, MqttModule establishes a persistent connection to the broker and subscribes to the single-level wildcard topic telematics/+/telemetry.

2. Validation & Device State

IngestionService extracts the vehicle IMEI from the topic. It updates the devices table record with last_seen, battery_level, and ignition status.

3. PostgreSQL Persistence

TypeORM inserts an immutable breadcrumb record into telemetry_records (latitude, longitude, speed, heading, timestamp) for historical trip playback.

Backend Ingestion Service Logic (NestJS):

// In src/modules/telemetry/ingestion.service.ts
@Injectable()
export class IngestionService implements OnModuleInit {
  onModuleInit() {
    this.mqttClient.subscribe('telematics/+/telemetry', { qos: 0 });
    this.mqttClient.on('message', async (topic, payload) => {
      const imei = topic.split('/')[1]; // Extracts IMEI from topic hierarchy
      const data = JSON.parse(payload.toString());

      // 1. Update Device live state in PostgreSQL
      await this.devicesService.updateLastSeen(imei, data);

      // 2. Persist historical telemetry record
      await this.telemetryRepository.save({
        deviceId: imei,
        latitude: data.lat,
        longitude: data.lng,
        speed: data.spd,
        ignition: data.ign === 1,
        timestamp: new Date(data.ts * 1000)
      });
    });
  }
}

3 MQTT Strategy: What We Currently Use vs. Future Cloud Broker

Our project uses a two-phase architecture roadmap to balance rapid prototyping with commercial fleet scalability:

Currently Used (POC / MVP Phase) CURRENT

Broker: HiveMQ Public Sandbox (broker.hivemq.com)

  • TCP Endpoint: mqtt://broker.hivemq.com:1883 (Backend & Trackers)
  • WebSocket Endpoint: wss://broker.hivemq.com:8884/mqtt (Web Dashboard)
  • Why we used it: Instant zero-friction setup. Requires no cloud hosting or SSL certificate generation during early UI and API development.
  • The Limitation: It is public to the entire world. Anyone can listen to our vehicle traffic (such as the TechPro_70001 stranger message seen in your console screenshot!).

Future Strategy (Commercial Production) FUTURE

Broker: Self-Hosted Eclipse Mosquitto on Cloud VPS (AWS / DigitalOcean / GCP)

  • Ports: Port 1883 (TCP for SIM Trackers) & Port 9001 (WSS via Nginx SSL)
  • Why we will switch to Mosquitto:
    • Zero Device Limit: No 25-device cap (can handle 10,000+ trackers).
    • Flat Low Cost: $4–$5/month fixed VPS vs thousands for enterprise HiveMQ.
    • 100% Data Sovereignty: Coordinates remain strictly inside our private VPS.
    • Sub-Millisecond Colocation: Internal Docker network latency drops to <0.5ms between Mosquitto and NestJS.

5 Explaining Every MQTT Concept Directly From Your Screenshot

Look closely at each component visible in your screenshot at http://192.168.1.60:5173/console:

1. Topic (The Channel Address) Addressing

In your screenshot's Publish panel, the Topic input currently contains: localhost.

Important Real-World Fix:

In MQTT, localhost is just treated as a random channel name like "sports" or "news". In a real telematics system, topics MUST follow a hierarchical address structure:
telematics/{imei}/telemetry → e.g. telematics/860000000000001/telemetry.
This allows the NestJS backend and web dashboard to distinguish between 10,000 different trucks and listen using wildcards (telematics/+/telemetry).

FAQ: "A vehicle only knows its IMEI number. Why do we need 'telematics' and 'telemetry'? Won't that confuse the vehicle?"

No, the hardware vehicle tracker never gets confused! Here is how it works in the real world:

  • 1. Tracker Firmware Auto-Fills the IMEI: Commercial GPS trackers (like Teltonika, Coban, Sinotrack, Concox) have a setting in their configuration tool: MQTT Topic: telematics/%IMEI%/telemetry. When the device boots up, its firmware automatically replaces %IMEI% with its hardware modem IMEI (e.g. 860000000000001). The hardware does this automatically in 0 milliseconds.
  • 2. A Vehicle Sends Multiple Types of Data (Not Just GPS): A vehicle is a complex machine that transmits different categories of messages:
    • GPS Coordinates: telematics/{imei}/telemetry (Sent every 5 seconds)
    • SOS Panic Crash Alert: telematics/{imei}/alarm (Critical alert event)
    • Engine Diagnostics / DTC Codes: telematics/{imei}/obd (Check engine errors)
    • Remote Control Commands: telematics/{imei}/cmd (Server tells car: "CUT_ENGINE")
    • Command Confirmation: telematics/{imei}/cmd/ack (Car tells server: "ENGINE CUT EXECUTED")
    If the topic was just the bare number 860000000000001, the server wouldn't know whether the incoming packet is normal GPS coordinates, an emergency crash alert, or a command confirmation!
  • 3. Wildcard Subscriptions (`+`) for 10,000 Vehicles: The NestJS backend listens using telematics/+/telemetry. A single wildcard + matches every vehicle in your fleet automatically. If topics were just bare IMEI numbers, the server would have to register 10,000 separate subscriptions!

2. Publish & Subscribe (Decoupled Messaging) Pub / Sub

Notice the message in your live feed: ↘ 15:32:11.200 TechPro_70001: "Ok bro I got your message".

Why Did "TechPro_70001" Appear in Your Screenshot?

Because you are connected to HiveMQ's public sandbox (broker.hivemq.com:1883). This broker is open to the entire world! Another developer named TechPro in another country was publishing on the same public broker, and because your console subscribes to # (everything), their message appeared in your feed! This is the #1 reason why we must self-host our own Mosquitto broker on our cloud server for real fleet tracking.

3. QoS (Quality of Service: 0, 1, 2) Guarantees

Notice the small gray badge `Q0` next to each message in your live feed:

  • QoS 0 (`Q0` in your screenshot): "At most once" (Fire & Forget). The tracker sends coordinates without waiting for an ACK. If cellular signal drops in a tunnel, the packet is ignored because the next ping 5 seconds later will replace it. Saves cellular SIM data costs.
  • QoS 1 (`QoS 1` button in your panel): "At least once". Requires a two-way handshake (`PUBACK`). Used for SOS emergency alerts and engine-cut commands.
  • QoS 2 (`QoS 2` button): "Exactly once". A 4-step handshake used for electronic toll booth payments.

4. Retain Flag (The Yellow 'R' Badge in Your Screenshot) State Cache

In your screenshot, look at message 15:50:09.490. It has a special yellow badge: R!

That `R` stands for RETAINED. Because the "Retain" toggle switch was turned ON when published:

The broker saved that exact message in its memory buffer. If you close your browser tab and reopen http://192.168.1.60:5173/console 10 minutes later, the broker will instantly push that retained packet at 0ms so your screen never starts blank!

5. Client ID (`tz-web-8wou-f173`) Session Isolation

Look at your Connection panel: Client ID: tz-web-8wou-f173.

MQTT brokers only permit ONE active connection per Client ID. If two browser tabs share the same ID, the broker kicks off the older tab in a loop. Our frontend automatically generates a unique random ID per tab stored in sessionStorage, allowing you to open 10 tabs simultaneously without disconnect storms.

7 🗺️ The Map Stack at a Glance (Leaflet & OpenStreetMap)

On our device tracking and detail pages (such as http://192.168.1.60:5173/devices/1 showing coordinates 11.71150, 78.08720 on the Bangalore-Salem highway), we built a high-performance, dark-themed mapping engine. Here is the exact technology stack powering the map:

Component Technology Used Why We Used It
Mapping Engine Leaflet.js (leaflet v1.9) Ultra-lightweight (only ~42 KB), open-source, mobile-friendly, and renders smoothly without CPU lag.
Map Tiles (Cartography) OpenStreetMap (OSM) 100% free global street tiles (https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png). Accurately shows the Bangalore-Salem Highway (NH7) and local streets in Tamil Nadu without any Google Maps billing fees.
Dark Theme Styling CSS Hardware-Accelerated Filters Converts standard light OpenStreetMap tiles into a modern dark theme using pure CSS (filter: invert(1) hue-rotate(180deg) brightness(0.85) contrast(0.9)). Zero external paid Mapbox subscriptions needed!
Vehicle Marker (Pin) L.circleMarker Vector Ring Renders crisp SVG vector circles on the exact GPS coordinates (11.71150, 78.08720) with a white outline border and dynamic green ignition-status color.
React Integration Custom React 19 Component Encapsulated in FleetMap with automatic viewport auto-centering (map.fitBounds), smart scrollwheel focus handling, and automatic resize detection (ResizeObserver).
The Dark Theme Filter in `src/styles/index.css`: 
/* Converts light OSM tiles to dark theme */
.dark .leaflet-tile {
  filter: invert(1) hue-rotate(180deg) brightness(0.85) contrast(0.9);
}

Inverts the bright street tiles while preserving true green hues for parks and road colors for highways.
