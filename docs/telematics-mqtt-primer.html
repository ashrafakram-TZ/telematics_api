Part 1

What telematics is

Telematics means a device in a vehicle sending its data to a server over the mobile network.

  • The device is a small GPS tracker in a truck, bus or car. It has a GPS chip, a SIM card, and wires to the ignition and fuel sensor.
  • What it sends: where it is (lat, lng), speed (spd), direction (hdg), whether the engine is on (ign), distance travelled (odo) and fuel level (fuel).
  • Identity: each device has a 15-digit IMEI, like a serial number. That is why devices.imei is the key in our API.
  • What the server does: receives the messages, stores them in the telemetry table, and shows live location, history and status, such as when the device was last seen (last_seen_at).
  • Later features: trips, geofences (alert when a vehicle leaves an area), overspeed alerts, fuel theft detection.

Why messages must stay small

Devices use mobile data, often on weak 2G or 4G, and they report all day. In the POC a device sends one reading every 5 seconds, which is about 17,000 messages per device per day (86,400 seconds ÷ 5). A fleet of 100 vehicles is 1.7 million a day. Every byte counts, so the payload uses short keys:

{ "ts": 1793259595, "lat": 13.0827, "lng": 80.2707, "spd": 42, "hdg": 180, "ign": 1, "odo": 12345.6, "fuel": 56 }
Part 2

What MQTT is

MQTT is a lightweight messaging protocol built for devices like these. It uses publish and subscribe through a middleman called the broker. Devices and our API both connect to the broker and never talk to each other directly.

  • Broker is the post office. Mosquitto, HiveMQ and EMQX are common ones. We use broker.hivemq.com:1883 for the POC.
  • Topic is the address on the message, such as telematics/860000000000001/telemetry.
  • Publish: the device sends a message to a topic. A publish topic must be exact: no + or #.
  • Subscribe: our API asks for every message on telematics/+/telemetry. The + matches any one level, so this means "any IMEI".
The topic is configurable

The API subscribes to the value of MQTT_TOPIC_FILTER in .env. If it is empty or missing, the API uses telematics/+/telemetry. The API reads the IMEI from the second part of the topic, so any custom filter must keep that shape: something/{imei}/something.

QoS: how hard the broker tries to deliver

QoSGuaranteeTrade-off
0Sent once, no confirmationCan be lost on a bad network
1Delivered at least onceCan arrive twice
2Delivered exactly onceSlowest, rarely used for telemetry

Telematics usually uses QoS 0 or 1. With QoS 1 the same reading can be stored twice. Our API does not remove duplicates yet (see Known gaps).

Why not plain HTTP

  • MQTT keeps one connection open, and each message has a header of only a few bytes.
  • It copes with weak or dropping networks and reconnects on its own.
  • The server can push commands back to the device on the same connection, for example "cut engine" on telematics/{imei}/cmd.
Part 3

How it works in real life

Nobody sends these messages by hand. The tracker's firmware builds the message and publishes it on its own, every few seconds, for as long as the vehicle has power. Our server is automatic too: it stays subscribed and saves each message as it arrives.

Where each field comes from

FieldSource on the device
tsGPS clock, so always current Unix time in seconds
lat, lng, spd, hdgGPS chip
ignWire connected to the ignition
odoDistance the device has calculated
fuelFuel sensor wire

Set up once per device

Each tracker is configured once, usually with the vendor's setup tool or by SMS commands:

  • the broker address (later our private broker)
  • its topic, telematics/{its IMEI}/telemetry
  • the send interval, for example every 5 seconds

The device never needs our server's URL. It only knows the broker. That is why the server can move, redeploy or change IP without touching a single vehicle.

Postman and MQTTX are fake devices

When we test, Postman plays the part of the tracker. {{$timestamp}} stands in for the GPS clock, and the fixed numbers stand in for the sensors.

Check the device model early

Many popular trackers (for example Concox and several Teltonika models) do not send JSON over MQTT. They use their own compact binary format over plain TCP. Ask the vendor: "Does this device support MQTT with a custom JSON payload?" If yes, our project works as it is. If no, we add a small protocol gateway that converts their format into our JSON (shown in the production diagram).

Part 4

Architecture of this base

One NestJS process does two jobs: it listens on MQTT for device readings, and it serves the REST API for people. Both sides share one PostgreSQL database.

Part 5

What happens to one message

Every reading passes four checks before it is saved. A message that fails any check is logged with the reason and dropped. It never stops the API.

How to check everything now

Work through these in order. Each step says what you should see. Replace localhost with 192.168.1.86 when testing from another machine.

  1. Start the API

    In VS Code: npm run start:local:win

    Expect the last log lines to include HTTP listening on http://192.168.1.86:3000/api and MQTT subscribed to telematics/+/telemetry. Keep this terminal open; if you see the PS C:\…> prompt again, the app has stopped.

  2. Check health

    GET http://localhost:3000/api/health

    Expect {"status":200,"message":"OK","data":{"db":"up","mqtt":"up"}}

  3. Open Swagger

    http://localhost:3000/api/docs (teammates: http://192.168.1.86:3000/api/docs)

    Expect Health, Devices and Telemetry groups. Swagger covers the REST side only; MQTT is documented on this page.

  4. Register a device

    POST http://localhost:3000/api/devices
{ "imei": "860000000000001", "name": "Truck 01" }

    Expect 201 with the new device and its id. Sending the same IMEI again gives 409 CONFLICT, which proves the error handler works.

    New → MQTT. URL mqtt://broker.hivemq.com:1883. In Settings, give it a unique Client ID such as postman-yourname-01. Click Connect.

    Expect "Connected to broker" and the status stays Connected.

Known gaps

    
    
      
  • No duplicate handling. With QoS 1 the same reading can be stored twice. The fix is a unique key on device and timestamp, with duplicate inserts ignored.
    • 
      
  • Public broker without login. Production needs a private broker with a username and password per device, plus TLS.
    • 
      
  • No API login. The REST endpoints have no authentication yet (JWT is planned).
    • 
      
  • No commands to devices. The telematics/{imei}/cmd topic is not built yet.
    • 
      
  • Plain PostgreSQL for telemetry. Large fleets will need a time-series setup such as TimescaleDB.
    • 
    

  


  
Payload rules: ts is current Unix time in seconds (10 digits), within the last 30 days and at most 5 minutes ahead; lat −90 to 90; lng −180 to 180; spd ≥ 0; hdg 0–359; ign 0 or 1; odo ≥ 0; fuel 0–100. Only ts, lat and lng are required. API times are returned in IST (+05:30) and stored in UTC.
